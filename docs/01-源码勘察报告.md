### 1.3 客户端选型结论（关键）

- **A 股行情**：优先用 `MacClient`（MAC 协议），其次 `UnifiedTdxClient`（自动路由）。
- **原协议 `TdxClient`** 单次 `get_security_bars` 最多 800 条、需自行分页；**MAC 协议 `MacClient.get_stock_kline` 内部自动分页（每页 700）**，更易用。
- **`from_best_host()` 有副作用**（写 `~/.easy_tdx/config.json`），量化生产环境应避免调用，改用显式 `host/port` 或 `config.get_known_hosts()`。

## ③ 扩展点分析（含调用代码片段）

### 扩展点 1：自定义因子（Factor + 注册表）
```python
# 继承 Factor，声明元信息，实现 compute 返回 pd.Series
from easy_tdx.factor.base import Factor, register_factor

@register_factor
class my_momentum(Factor):
    name = "my_momentum_10d"
    category = "momentum"
    description = "10日自定义动量"
    inputs = ["close"]

    def compute(self, df: pd.DataFrame) -> pd.Series:
        return df["close"].pct_change(10)

# 即被 FACTORY_REGISTRY 收录，可直接用于 FactorEngine.compute_cross_section
```
**可用性**：★ 完整、文档化、有 builtin 范例。

### 扩展点 2：自定义权重优化器（WeightOptimizer）
```python
from easy_tdx.portfolio.optimizer import WeightOptimizer, register_optimizer

@register_optimizer
class MyOptimizer(WeightOptimizer):
    name = "my_opt"
    def optimize(self, scores: pd.Series, **kwargs) -> pd.Series:
        # 返回归一化权重
        return scores.clip(lower=0) / scores.clip(lower=0).sum()

# 注入 RebalanceEngine(optimizer=MyOptimizer())
```
**可用性**：★ 可直接替换 `RebalanceEngine` 的 optimizer 参数。

### 扩展点 3：自定义滑点 / 执行模型（回测）
```python
from easy_tdx.backtest.slippage import SlippageModel
from easy_tdx.backtest.execution import ExecutionModel

class RealisticSlippage(SlippageModel):
    def apply(self, price, size, side, ctx): ...

class RealisticExecution(ExecutionModel):
    def execute(self, order, ctx): ...

BacktestEngine(strategy, slippage_model=RealisticSlippage(), execution_model=RealisticExecution())
```
**可用性**：★ 抽象清晰，用于实盘成本建模。

### 扩展点 4：缠论增量计算的"伪增量"处理（需自研补偿）
```python
# 原项目 append_klines 是 concat 后全量重算 —— 非真增量
analyser = ChanlunAnalyser(code="600000", frequency="5min")
res = analyser.process_klines(history_df)          # 全量
# 实盘逐 bar：
res = analyser.append_klines(new_bar_df)            # 实为 concat+全量重算，O(n) 每 bar
```
**结论**：高频实盘逐 bar 推进不可直接依赖 `append_klines`。建议自研"缓存 + 阈值触发全量重算"或自研增量缠论算法；Kuantix 实盘监控模块需在此处自建增量逻辑。
**可用性**：△ 需自研补偿层。

### 扩展点 5：Web 宿主挂载（Kuantix 集成 easy_tdx 后端）
**已实测**（环境 fastapi 0.139.0）：
- 实验1：SPA `mount('/')` 之后 `include_router` 新路由 → **404（被吞）**；
- 实验2：把新路由插入 mount 之前（重排 routes）→ 200；
- 实验3：Kuantix 做宿主 `host.mount('/tdx', easy_tdx_app)` → `/api/Kuantix/*`、`/tdx/api/v1/*`、`/tdx/` 均 200；
- 实验4：子应用 lifespan 默认**不**被宿主触发（`events fired: []`）；
- 实验5：宿主用 `async with sub.router.lifespan_context(sub)` 手动驱动 → 正常触发（client=CONNECTED）。

```python
# 推荐方案：Kuantix 作为宿主，mount easy_tdx 于 /tdx，并手动驱动其 lifespan
import easy_tdx.web as etdx_web
from contextlib import asynccontextmanager
from fastapi import FastAPI

etdx_app = etdx_web.create_app()

@asynccontextmanager
async def lifespan(app: FastAPI):
    async with etdx_app.router.lifespan_context(etdx_app):  # 手动驱动子应用 lifespan
        yield

host = FastAPI(lifespan=lifespan)
host.include_router(Kuantix_router, prefix="/api/Kuantix")
host.mount("/tdx", etdx_app)
```
**可用性**：★ 方案B 可行且推荐（见⑥ Web 扩展推荐）。

## ④ 耦合风险清单

| # | 风险 | 位置 | 影响 | 缓解 |
|---|------|------|------|------|
| R1 | `from_best_host()` / `save_best_host` **写全局 `~/.easy_tdx/config.json`** | `client.py` / `config.py` | 多进程/容器环境互相覆盖配置；非幂等 | Kuantix 用显式 `host/port` 或 `config.get_known_hosts()`，禁止调用 `from_best_host` |
| R2 | `TdxConnection` **单连接 + threading.Lock + 守护心跳线程**，非并发安全；`BacktestTaskRunner` 为进程级单例 | `transport/sync.py` / `web/task_runner.py` | 多 worker 并发抢同一连接；线程池单例在 fork 下状态异常 | 每进程独立客户端实例；监控模块用 `AsyncMacClient` 规避 GIL/锁 |
| R3 | `offline/detect_tdx_home()` **自动探测**依赖本地通达信（`TDX_HOME` / `C:\new_jyplug`）+ pandas `<3` 约束 | `offline/paths.py` / `pyproject.toml` | ⚠**已纠正**：`offline` 写侧 API 不要求本地通达信——`resolve_vipdoc(path)` 仅 `is_dir()` 校验（`paths.py:52-56` 已核实），自建 `~/.Kuantix/vipdoc` 即可；pandas 3.x 仍不兼容 | DataLake **始终显式传 `vipdoc_path`**，绝不调用 `detect_tdx_home`；锁定 `pandas>=2.0,<3`（见⑧） |
| R4 | `realtime` 仅为骨架，`/ws/realtime` 的 `event_bus` **从未被填充** | `realtime/engine.py` / `web/routers/realtime.py` | 实时推送无数据源，不能直接用 | 自建数据源注入 `EventBus`（轮询 `get_security_quotes` 或 WS） |
| R5 | SPA `mount('/')` 吞掉其后路由 | `web/app.py` | 不能在原 app 追加路由 | 用方案B（宿主 mount），勿改原 app 路由 |

## ⑦ Web 层扩展推荐方案与版本/依赖约束

### 7.1 Web 扩展推荐方案

**推荐方案 B（Kuantix 做宿主，easy_tdx 以子应用挂 `/tdx`，并手动驱动其 lifespan）**：
- 优势：零改动原项目、路由命名空间隔离、`/api/Kuantix/*` 与 `/tdx/api/v1/*` 共存；前端可独立部署或 embed。
- 必须手动驱动子应用 lifespan（`async with etdx_app.router.lifespan_context(etdx_app)`），否则共享连接不初始化（见③扩展点5 实验4/5）。
- **不推荐**改原 `app.py` 路由（SPA 吞路由 + 违反硬约束）。
- **备选**：Kuantix 完全独立 FastAPI + 独立前端（Vue3+Vite+ECharts+Pinia，参考 easy_tdx 的 `web-ui/dist` 结构），仅后端 `import` easy_tdx 数据/因子/回测层，Web 层不 mount 原 app。更解耦，但失去现成 SPA。

### 7.2 版本与依赖约束建议

| 约束 | 建议 |
|------|------|
| Python | `>=3.10`（与 easy-tdx 对齐）；建议 3.11 |

## ⑧ 补充：L1 vipdoc 数据湖可行性（回应 PRD v2.0 重大发现）

PRD v2.0 指出 macOS 无本地通达信、无 vipdoc 目录，原"本地 vipdoc"假设不成立。经**逐文件核对源码**，确认"自建 `~/.Kuantix/vipdoc` + 用上游写侧落原生格式"方案可行，且 `SignalScanner` 等读侧零改造可用。本节为对 PM 发现的验证与设计约束沉淀（属勘察范围的补正，非新架构）。

### 8.1 三条硬证据逐一核实（均 ✅ 成立，附 file:line）
1. `resolve_vipdoc(path)`（`offline/paths.py:52-56`）：显式 path 仅 `p.is_dir()` 校验，**不验证是否真实通达信安装** → 传 `~/.Kuantix/vipdoc`（只要它是目录）即可。
2. 上游写侧完整存在：
   - A股日线：`sync_daily_bars_from_security_bars(filepath, server_bars, price_coeff, vol_coeff)`（`write_daily.py:175`）；`append_daily_bars`（`:126`）内部 `_repair_tail`+`get_last_bar_date`+日期去重+`f.flush()/os.fsync()`。
   - 扩展市场：`sync_ex_daily_bars(filepath, server_bars)`（`write_ex_daily.py:84`），用 `ExDailyBar`（float32，无系数）。
   - 分钟线：`append_5min_bars` / `append_lc_min_bars`（`write_min_bar.py:87 / 162`）+ `get_last_*_datetime` 断点。
3. 增量/容错白送：`get_last_bar_date`（`write_daily.py:60`）给断点；`append_daily_bars` 日期去重 + `_repair_tail` + fsync；`SignalScanner` 另用 mtime 增量缓存（`scanner.py:154-174`）。

### 8.2 读侧零改造可用的核实
- `SignalScanner.__init__` → `resolve_vipdoc(vipdoc_path)`（`scanner.py:93`）；`_collect_files` 扫 `{vipdoc}/{exchange}/lday/*.day`（`scanner.py:371-377`）；`_scan_one` → `read_daily_bars`（`scanner.py:460`）解码。
- 目录布局由我们掌控：`find_daily_bar_file` / `read_daily_bars` 约定 `{vipdoc}/{exchange}/lday/{exchange}{code}.day`（与 `_collect_files` 一致）。

### 8.3 DataLake（L1）设计约束（架构阶段必须落实，否则数据损坏/读错）
- **RD-1 系数一致性（高优先级）**：`encode_daily_bar` 用我们传入的 `price_coeff/vol_coeff`；但读侧 `read_daily_bars` 依**文件名代码段**经 `_detect_security_type`+`_SECURITY_COEFFICIENTS`（`daily_bar.py:15-72, 88-89`）反推系数。二者必须一致，否则解码价格错 10×。DataLake 写 A股（`00/30`sz、`60/68`sh）用 `(0.01,0.01)` 与读侧推断一致；若写基金/ETF/指数须用对应系数。建议 DataLake 复用同一张系数表，禁止硬编码。
- **RD-2 fsync 非对称（崩溃恢复）**：仅 `append_daily_bars` 有 `flush+fsync`；`append_ex_daily_bars`/`append_5min_bars`/`append_lc_min_bars` **无**。A股日线崩溃安全；扩展市场/分钟线中途崩溃可能留半条残记录（且 ex/min 读侧无 `_repair_tail`）。DataLake 对 ex/min 写入须自行补 `fsync` 或写入后校验。
- **RD-3 目录布局**：日线严格 `{vipdoc}/{sz|sh}/lday/{exchange}{code}.day`；分钟线遵循 TDX 约定（`{exchange}/minline/...`，读侧收显式 path，内部布局自定一致即可）。
- **RD-4 扩展市场布局自定**：`_market_to_exchange`（`paths.py:68-74`）仅映射 SZ/SH、其余抛错；港美股须走 `ex_daily` 路径且目录布局我们自定（如 `{vipdoc}/hk/lday/...`、`{vipdoc}/us/lday/...`）；`SignalScanner` 只扫 `sh/sz` A股，**不会读港美股**（符合 P0 仅 A股完整实现、港美股 P1 的约束）。
- **RD-5 原始价 vs 复权**：`sync_*` 直接编码 `server_bars` 的 OHLC。若服务端返回 QFQ，则 L1 变 QFQ 数据集。须明确 L1 存**原始未复权**价、复权在 L2 派生，避免与上游 `Adjust.QFQ` 语义混淆。

### 8.4 对三大模块复用结论的修正
- **选股**：原评"≈50% 混合、在线接入需自研" → 修正为"≈60–70%"。L1 写侧解锁 `SignalScanner` 全市场离线扫描（零改造），自研量收敛到"在线拉取→写 vipdoc→调度/增量编排"。
- **回测**：`RebalanceEngine`/`FactorEngine` 吃 DataFrame，L1→L2（Parquet）派生后即可喂，不受影响。
- **监控**：不变（仍靠 `AsyncMacClient.get_security_quotes` 轮询 + 自建 `EventBus` 注入）。

### 8.5 关联 PRD v2.0 其它约束（架构阶段承接）
- **MarketProfile（NF-5~NF-8）**：±10%、100股/手、252交易日、CNY、UTC+8 等一律走 `MarketProfile`，业务代码禁硬编码；港美股未实现显式抛错、不准静默降级；接口签名 P1 不变。影响 factor/monitor/screen 三模块——与"四模块禁互 import、跨模块走 `core` 契约"共同决定 phase-2 包结构。
- **NF-20**：可**只读**复用 `~/.easy_tdx/config.json` 已知最优节点（52 个 known_hosts），免重复测速；**禁止写入上游目录**（呼应 R1）。
- **NF-21 红线**：代码库不得含任何券商下单/资金接口，下单仅 CSV 导出（P1）。
- **插件扩展点 6 类**：因子、预警判据、推送通道、选股过滤器、券商 CSV 模板、市场档案——`core` 须提供统一插件契约（注册表+装饰器）。
