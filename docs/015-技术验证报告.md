## 0. 结论先行（给 team-lead）

**S1–S5 五项技术验证全部通过，可以进入架构设计（Phase 2）。**

但门禁期间实测推翻了 3 项原有假设、并新发现 3 项数据层风险（RD-8、uint32 余量仅 1.1×、`GetSecurityListCmd` 连接复用 15s 陷阱）。这些结论**必须作为架构设计的硬前置约束**写入 `system_design.md`，否则 DataLake 写入链路会在上线后静默损坏数据。

进入架构设计的 **5 条前置约束**（详见 §5）：
1. A 股全市场枚举必须**每页新建连接**，禁止同连接复用 `get_security_list`（否则每页 ≈15s 超时）。
2. DataLake 写盘前 `vol` 必须**股→手（÷100）**换算（RD-8），否则 uint32 溢出。
3. 写入前必须做 **uint32 上界校验**（000100 单日量已占上限 90.9%，余量仅 1.1×）。
4. 港美股必须走**独立 `MacExClient(7727)` + `goods_kline`** 链路，不能与 A 股 `MacClient(7709)` 混用。
5. 回补（建湖/增量）与盘中监控轮询必须**独立连接/进程 + 错峰**（NF-28）——本报告的 `run_all` 编排实测已复现"重枚举后紧接拉取被服务端限速挂起"的现象，直接印证 NF-24/NF-28。

### S3 — vipdoc 数据湖端到端闭环（无本地通达信安装）

| 步骤 | 实测数字 | 结论 |
|------|----------|------|
| 1 建目录 | `~/.Kuantix/vipdoc/sh/lday`（纯自建，无通达信） | 路径自掌控可行 |
| 2 在线拉取 | 600000 → 2400 行 / **0.37s** | 数据源可用 |
| **2b RD-8 vol 单位** | 不换算直接编码 → overflow（3.797e10 > uint32max）；÷100 后余量 **11.3×** | ⚠️ **`MacClient.get_stock_kline` 的 `vol` 单位是「股」**，写盘必须 ÷100 |
| 3 写入 | 2400 条 / 1.8ms，size 76800B（**32B/根**） | 原生格式落盘 |
| 4 读回 | 2400 条 / 2.0ms | 读侧可用 |
| 5 字段比对（RD-1 正面） | 价格 max_rel_diff **6e-8**、vol/amount 0 差 | ✅ 系数一致时读回无损 |
| **5b RD-1 反面** | sh510300 识别为 `SH_FUND` 读系数 (0.001,1.0)，用 0.01 写 → 读回 0.985 vs 写入 9.85（**×0.10**） | ⚠️ 系数错配 = 静默 10× 错价，陷阱坐实 |
| 6 SignalScanner 扫描 | 1 信号 / 0.02s，命中 600000 | ✅ 读侧零改造可用（PRD 0.3 核心假设成立） |
| 7 幂等 | 重写同批实写 0 条，2400→2400 | ✅ 日期去重 OK |
| 8 崩溃自愈 | 残尾 15B → `get_last_bar_date` 只读不改；append 1 后 size%32=0 | ✅ `_repair_tail` 自愈 OK |
| 9 写盘吞吐外推 | 20×2400=0.03s → 全 A ≈8s，磁盘 ≈**396MB** | 落盘轻量 |
| **10 uint32 余量** | 抽样 100 只×10 年，最差 000100 单日 **3,843,857,664 股** → 编码值 3.844e9，占用上限 90.9%，**余量仅 1.1×** | ⚠️ 逼近溢出，高换手大盘股危险 |

**结论**：vipdoc 原生格式数据湖闭环完全跑通；`SignalScanner` 零改造可用。但 **RD-8（vol 单位）+ uint32 余量 1.1× + RD-1（系数）** 三条必须在写入链路前置处理，否则静默损坏。

## 3. 被推翻的假设（3 项）

| # | 原有假设 / 设计预期 | 实测推翻结论 | 对架构的影响 |
|---|---------------------|--------------|--------------|
| **A1** | 港美股可复用 A 股 `MacClient(7709)` + `ExMarket` 取数 | ❌ 实测必须用 **`MacExClient(7727)` + `goods_kline`**（`MacClient` 不返回扩展市场数据） | 港美股数据接入须为**独立客户端 + 独立数据路径（ex_daily）**，不能并入 A 股拉取器 |
| **A2** | `vol` 字段单位已是「手」（与 vipdoc 约定一致） | ❌ `MacClient.get_stock_kline` 返回的 `vol` 是**「股」**；直接 `int(vol/vol_coeff)` 编码会溢出 uint32 | DataLake 写盘前必须 `vol ÷ 100`（股→手），否则大成交量股票溢出 |
| **A3** | `get_security_list` 同连接复用安全高效 | ❌ 同连接第 2 页起每页 ≈**15s**（read timeout 触发重试阶梯后重连），每页新连接仅 ≈0.03s | 全 A 枚举 / 增量更新的枚举步骤**必须每页新建连接**，否则 52 页会从 6s 退化到 ~13 分钟 |

## 4. 新发现 / 确认的数据层风险

| # | 风险 | 实测证据 | 严重度 | 处置（落到架构/NF） |
|---|------|----------|--------|---------------------|
| **RD-8**（新） | `vol` 单位是股，编码前需 ÷100 | 600000 单日 3.797e8 股，不换算编码值 3.797e10 > uint32max；÷100 后余量 11.3× | 高 | DataLake 写盘前强制 `vol ÷ 100`；单测覆盖 |
| **RD-9**（新） | uint32 余量仅 1.1× | 000100 单日 3.843e9 股 → 编码 3.844e9，占上限 90.9% | 高 | 写入前 **uint32 上界校验**，超限按 NF-26 报错进隔离区；或评估 float32/更大整型 |
| **RD-10**（新） | `GetSecurityListCmd` 连接复用 15s 陷阱 | A0 实验：复用 [0.04,15.36,15.21] vs 新连 [0.04,0.03,0.03] | 中 | 枚举器封装「每页新连接」；隐藏此陷阱于 `adapters` 层 |
| RD-1（确认） | 系数不一致 → 10× 错价 | 5b：sh510300 错系数写读回 ×0.10 | 高 | NF-25 系数表 import 引用 + 写前按文件名判定系数 |
| RD-2（确认） | fsync 非对称（仅 A 股日线有） | S4：`append_ex_daily_bars` 无 fsync | 中 | ex/分钟线写入自补 `fsync` + 写后回读校验（NF-27） |

> RD-1/RD-2 已在 `docs/01` 与 PRD §0.3.1 记录，此处为**实测再次确认**；RD-8/RD-9/RD-10 为本门禁期新发现。

## 5. 对架构设计的硬前置约束（必须写入 system_design.md）

将上述结论沉淀为 5 条不可协商的架构约束：

1. **枚举器（UniverseEnumerator）每页新建 `TdxClient` 连接**，禁止复用（RD-10 / A3）。
2. **DataLake 写入器在编码前做 `vol ÷ 100`（股→手）**（RD-8 / A2），并做 **uint32 上界校验**，超限按 NF-26 显式报错 + 进隔离区（RD-9）。
3. **系数表从上游 `import` 引用，禁止复制**（NF-25）；写入系数由「读侧判定逻辑」反推决定（按文件名代码段），杜绝 T1/T2 静默兜底。
4. **港美股链路独立**：`MacExClient(7727)` + `goods_kline` → `sync_ex_daily_bars` → `ex_daily` 目录；与 A 股 `MacClient(7709)` 物理隔离（A1）。
5. **回补链路与监控链路资源隔离**（NF-28）：独立连接/进程 + 错峰调度（交易时段禁止全量回补）；本次 `run_all` 实测已复现「重枚举后紧接拉取被服务端限速挂起」，直接印证 NF-24/NF-28 的工程必要性。

## 6. 统一编排 `run_all.py` 说明

`run_all.py` 按 S1→S5 顺序调用各 spike 的 `main()`，单 spike 异常不影响其余。

- **首次编排（run_all.log）**：S1/S5/S2 均正常输出通过；在 S2（52 页枚举 + 300 只×10y 重拉）紧接 S3 的网络拉取时，S3 步骤 2 的在线拉取被服务端**限速挂起**，进程在 65s 后退出（EXIT=1），日志止于 S3 头。
- **复跑确认（run_all2.log）**：S1（`15/15`）、S5（`pass`）、S2（`pass`，含全量数字）三者**在统一编排中稳定通过**；S3 再次在起点出现后台沙箱的 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]` 守卫并挂起（非交互后台模式下阻塞），S4 未及运行。
- **独立复跑**：单独 `python -u S3_vipdoc_e2e.py`（沙箱已放行）**稳定 `status=pass`**；S4 此前独立运行亦 `pass`。两 spike 均非代码缺陷。
- **解读**：编排层的两次 stall 是**环境层**因素叠加——① S2 重枚举/重拉后服务端对同节点短时高频繁连接**限流**（恰好验证 NF-24/NF-28）；② 后台非交互模式触发沙箱批量删除守卫而阻塞。二者均**不影响 spike 正确性**，且 ① 本身就是 NF-24/NF-28 的工程实证。架构须内置请求限速、退避重试、连接配额，并严格执行回补/监控链路隔离。

> 五项 spike 的**独立运行结果均稳定通过**，结果 JSON 已全部落盘（`results/S1..S5_*.json`），作为本报告数字来源；其中 S1/S5/S2 另在统一编排中复测通过。
