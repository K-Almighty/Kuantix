## 1. 问题 1：选股回测功能缺失

### 1.1 上游能力清单（easy_tdx web-ui + backtest 引擎）

**上游 web-ui**（`easy_tdx-main/web-ui/src/views/BacktestView.vue`，509 行）UI 结构：
- 左配置面板：
  - 行情数据：`SymbolPicker`（代码/周期/起止日期）
  - 策略：`StrategyPicker`（从 `/backtest/strategies` 加载策略列表 + 参数 schema 动态渲染表单）
  - 资金与成本：初始资金 / 佣金率 / 滑点 / 成交价（next_open/next_close）
  - 「开始回测」按钮（自动取行情 → 回测）
- 右报告面板：
  - K线+买卖点（`KlineChart`）
  - 净值曲线与回撤（`EquityChart`）
  - 评级（`GradeDetails`）
  - 绩效指标表（`MetricTable`：19 项指标）
  - 成交记录表（`TradeTable`）
  - 保存策略（`/strategies` 路由，SQLite `strategy_store`）

**上游 API 端点**（`src/easy_tdx/web/routers/backtest.py`）：
| 端点 | 说明 |
|---|---|
| `GET /backtest/strategies` | 枚举所有预置策略 + 参数 schema（`get_registry().all()` → `to_schema()`） |
| `POST /backtest/run` | 同步回测（必须内联 ohlcv） |
| `POST /backtest/run/async` | 后台任务回测（内联数据或按 symbol 取行情），返回 task_id（202） |
| `GET /backtest/tasks` | 最近 N 个任务摘要 |
| `GET /backtest/tasks/{task_id}` | 任务状态；done 时 result 含完整结果 |
| `POST /backtest/portfolio/run/async` | 组合（多标的）回测 |
| `POST /backtest/optimize/run/async` | 参数网格寻优 |

**上游策略注册表**（`src/easy_tdx/backtest/strategies/registry.py` + `builtin.py`）：
- 实测 **19 个策略**：ma_cross / macd / boll_breakout / rsi_reversal / kdj_cross / ema_cross / triple_ma / donchian / keltner / bbi / cci / wr_reversal / bias_reversal / dmi / trix / emv / dpo / atr_breakout / fsl
- 每个策略有 `name / label(中文) / description / params(list[Param])`，Param 含 `name/type/default/min/max/choices/label/description`

**上游引擎**（`src/easy_tdx/backtest/engine.py` + `types.py` + `performance.py`）：
- `BacktestEngine(strategy, cash, commission, min_commission, stamp_tax, slippage, execution)` → `run(df) -> BacktestResult`
- `BacktestResult`: `performance(dict, 19 项) / equity_curve(DataFrame: total, drawdown 等) / trades(DataFrame) / positions(DataFrame) / config / diagnostic`
- `PerformanceAnalyzer` 产出 19 项指标：total_return / annual_return / max_drawdown / max_dd_duration / sharpe / sortino / calmar / total_trades / win_trades / lose_trades / rejected_trades / win_rate / profit_factor / avg_win / avg_loss / max_win / max_loss / avg_holding_days / volatility

### 1.2 Kuantix backtest_bridge 现状与缺口

`Kuantix/adapters/backtest_bridge.py` 已包装：`BacktestEngine`（单标的）、`RebalanceEngine`、`SignalScanner`、`ChanlunAnalyser`、`StrengthRanker`。

**缺口（支撑完整回测页所需）**：
| 能力 | 现状 | 缺口 |
|---|---|---|
| 策略发现 | ❌ 无 `list_strategies` | 需要：按名称枚举策略 + 参数 schema（供前端表单） |
| 策略构建 | `run_backtest(df, strategy_cls)` 只接受策略类 | 需要：按 `strategy_name + params` 从注册表构建实例 |
| 参数透传 | 只透传 `cash` | 需要：cash/commission/min_commission/stamp_tax/slippage/execution |
| 结果结构 | 只返回 5 个指标 | 需要：完整 performance + equity_curve 序列 + trades 明细 + diagnostic |
| 数据源 | 调用方自备 df | 回测页需要「代码池 → L1 本地日线」的数据加载（复用 `L1Reader` 模式，全程本地不走网络） |
| 任务管理 | ❌ 无 | 复用现有 `JobManager`（SQLite 持久化，queued→running→done/failed） |

### 1.3 设计决策

1. **路由路径**：`/api/v1/backtest/*`（strategies / run / jobs/{id} / results/{id}）。⚠️ R5 收窄：路径不含 order/trade/buy/sell；回测内部分词为「回测模拟撮合」，命名走收窄词表（`run_backtest`、`equity_curve` 等安全）。
2. **引擎调用**：扩展 `BacktestBridge`（仍走 adapters，R2）：
   - `list_strategies()` → 上游 registry `to_schema()` 全量
   - `run_backtest(df, strategy_name, params, *, cash, commission, min_commission, stamp_tax, slippage, execution)` → 构建策略实例 → 引擎 → 返回完整结果 dict（含 equity_curve 序列、trades 明细）
3. **结果存储**：新增 `BacktestResultStore`（SQLite `~/.Kuantix/db/backtest_results.db`，表 `backtest_results(job_id PK, result_json, created_at)`）。Job 的 `result_summary` 只存轻量摘要（performance 指标 + 净值点数 + 成交笔数），完整结果按 job_id 查结果表 —— 避免大 JSON 塞进 jobs 表。
4. **数据加载**：新建 `Kuantix/backtest/service.py`（业务层，不直接 import easy_tdx）：`load_pool(codes, start, end)` 经 `L1Reader` 读本地 vipdoc 日线 → 每标的 DataFrame（含 datetime 列）→ 按日期过滤 → 逐标的跑 bridge。
5. **多标的语义**：单标的回测（一次一个标的池，逐标的出净值曲线 + 组合视角的总净值 = 各标的净值等权平均）。组合引擎（PortfolioBacktestEngine）上游存在，但多标的等权资金分配语义与「选股回测」（对选股结果逐标的验证策略）诉求不完全一致；P0 先做「逐标的 + 组合等权净值」的轻量聚合（在 service 层聚合，不重复实现绩效计算 —— 每标的绩效仍由上游引擎算）。

## 2. 问题 2：因子库数量不足

### 2.1 实测：上游注册因子 = 19 个（不是 ~45）

`easy_tdx.factor.builtin` 导入全部 7 子模块后，`FACTORY_REGISTRY` 实测 **19 个**：

| category | factors |
|---|---|
| chanlun | chanlun_bi_dir, chanlun_mmd |
| momentum | momentum_20d, momentum_60d, reversal_5d |
| quality | max_drawdown_20d, sharpe_20d, win_rate_20d |

| value | pb_ratio, pe_ratio |
| volatility | atr_14d, turnover_rate, volatility_20d |
| volume | amount_ma_ratio, obv_trend, vol_surge |

（任务描述中"每模块约 5-7 个、粗算 ~45"是错误估计；各模块实际 2-3 个。）

### 2.2 Kuantix 后端现状：已暴露 21 个（19 上游 + 2 自定义）

`FactorService.list_factors()` 实测返回 **21 个** = 19 上游 + `volume_ratio_5d`（自定义）+ `close_position_20d`（自定义）。`GET /api/v1/factor` 走 `FACTORY_REGISTRY` 自动发现，**后端无缺口**。

### 2.3 真正的缺口：前端 mock

`web/src/mocks/factor.ts` 的 `MOCK_FACTORS` 只有 **9 个**，且其中 **6 个名字是编造的**（与后端真实注册表不一致）：
- 编造：`pe_inv`（真实 `pe_ratio`）、`pb_inv`（真实 `pb_ratio`）、`roe`（上游无）、`turnover_20d`（真实 `turnover_rate`）、`ma_cross`（因子无此名）、`chanlun_second_buy`（真实 `chanlun_bi_dir`/`chanlun_mmd`）
- 缺失：12 个真实因子未在 mock 展示

→ 用户看到"数量不足 + 名字对不上"，根因在 mock 数据层。

### 2.4 修复方案

- 前端 mock `MOCK_FACTORS` 改为与后端一致的全量 **21 个**（category 用中文映射、source builtin/custom、status 按有无 years 模拟、display_name 用中文可读名）
- 后端零改动（已全量暴露）
- 补充：`docs/api-contract.md` 因子清单表格注明「上游注册 19 + 自定义 2 = 21」的现状口径

## 3. 问题 3：自选股刷新重置

### 3.1 实测行为

| 模式 | 行为 |
|---|---|
| mock（`VITE_USE_MOCK=true`，默认） | `web/src/mocks/monitor.ts` 的 `MOCK_WATCHLIST` 是**模块级数组**；`postWatchlist` 直接 `push` 进数组 → 刷新页面后模块重新加载 → **重置** ❌ |
| 真接口（`VITE_USE_MOCK=false`） | 后端 `MonitorStore`（SQLite `~/.Kuantix/db/monitor.db` 表 `watchlist`）`add_watch` 用 `INSERT OR REPLACE` → **已持久化** ✓；前端 `postWatchlist` 调 `POST /api/v1/monitor/watchlist` 端点正确（M5） |

### 3.2 根因

**mock 模式无持久化**（内存态数组）。真接口模式无 bug（SQLite 持久化链路完整：router → MonitorLoop.add_watch → MonitorStore.add_watch）。

### 3.3 修复方案

给 mock 的 `watchlist / positions / rules` 加 **localStorage 持久化**（模拟持久化语义，刷新保留）：
- `web/src/mocks/seed.ts` 加 `loadLocal<T>(key, fallback)` / `saveLocal<T>(key, value)` 工具
- `mocks/monitor.ts` 的 `MOCK_WATCHLIST / MOCK_POSITIONS / MOCK_RULES` 改为从 localStorage 初始化（首次无则用种子数组并写回）；写操作同步持久化
- 注意：localStorage 只在浏览器可用，模块加载时需 `typeof localStorage !== 'undefined'` 守卫（build/test 环境）

## 4. 问题 4：股票搜索只支持代码

### 4.1 现状

- 后端：`UniverseEnumerator` 产出 `Security(code, exchange, market, security_type, name)` —— **含 name** ✓；但枚举走网络（get_security_list），不适合每次搜索都枚举
- 前端：Monitor.vue 自选添加是「6 位数字逗号分隔」输入，无名称搜索、无下拉确认；Screen.vue 无标的搜索

### 4.2 方案

1. **后端** `GET /api/v1/data/search?q=<代码或名称>&market=CN&limit=20`（D8 增量端点，向后兼容）：
   - 数据源：`SecuritySearchService`（新 `Kuantix/data/security_search.py`）：
     - 证券清单**缓存**到本地 JSON `~/.Kuantix/db/security_catalog.json`（首次枚举后落盘，之后读缓存；缓存不存在且枚举失败 → fail-loud 显式报错，不静默空返回）
     - provider 可注入（测试注入假证券清单，不发网络）
   - 匹配：代码精确匹配优先 → 代码前缀匹配 → 名称子串匹配（模糊）
   - 返回 `[{code, name, exchange, market, security_type}]` 基本信息
   - `q` 空 → 400；无匹配 → **显式空数组**（合法态）；枚举源不可用 → 422 fail-loud
2. **前端**：
   - `web/src/types/data.ts` 加 `SecurityHit` DTO
   - `api/types.ts` + `client.ts` + `mocks/index.ts` 加 `searchSecurities(q, market)` 
   - Monitor.vue 自选添加区：输入框支持代码或名称，下拉展示 `代码 名称 (交易所/类型)` 供确认，选中后填入 code
   - Screen.vue / 回测页：标的池选择同样接入

## 6. 需要主理人注意的架构决策

1. **回测结果存储**：新增独立 SQLite 表 `backtest_results`（job_id → 完整结果 JSON），而非塞进 JobManager 的 result_summary。理由：净值序列 + 成交明细可达数十 KB，jobs 表存轻量摘要即可；结果表独立便于未来做结果对比/历史清理。**如主理人希望结果只存内存，可改为 Job result_summary 全量承载（影响：重启丢历史结果）。**
2. **因子数量口径**：上游实测 19（非 ~45），Kuantix 已 21。**用户"数量不足"的感知来自前端 mock**；后端不改。若用户期望"比上游更多"，那是自定义因子扩展需求（P1），不在本次修复范围。
3. **回测多标的口径**：P0 用「逐标的回测 + 组合等权净值聚合」，不引入 PortfolioBacktestEngine 的资金分仓语义（与"选股回测"诉求更贴合）。
