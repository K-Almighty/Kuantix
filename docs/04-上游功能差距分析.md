# Kuantix 上游功能差距分析（Gap Analysis）

> 作者：software-product-manager（Alice）　时间：2026-08-02
> 上游参考：`easy_tdx-main` v1.20.3 web-ui（只读）
> 现状基线：Kuantix `web/src/router/index.ts`（/factors /monitor /screen /backtest）+ 后端 `Kuantix/api/routers/`（data/factor/screen/monitor/backtest B1–B4）
> 用途：作为后续架构设计（docs/05）与实现排期的输入。

---

## 0. 结论摘要

上游 web-ui 共 **6 个页面**（单标的回测 / 组合回测 / 参数寻优 / 结果对比 / 策略库 / 服务器设置）。
Kuantix 当前 4 页，其中 **/backtest 只对齐了上游"单标的回测"约 50% 的功能点**（且为多标的聚合模式，与上游单标的模式语义不同），**组合回测 / 参数寻优 / 结果对比 / 策略库 / 服务器设置 5 页完全缺失**。

| 维度 | 结论 |
|---|---|
| 已对齐 | /backtest 的标的池、策略动态参数表单、资金成本配置、净值曲线、绩效指标、成交明细、导出（部分为 Kuantix 超集） |
| 完全缺失页面 | /portfolio 组合回测、/optimize 参数寻优、/compare 结果对比、/strategies 策略库、/settings 服务器设置 |
| 单页内缺失功能 | K线+买卖点、评级系统（A–D + 一票否决）、19 项绩效指标表、保存策略、URL query 深链回填、周期（WEEK/MONTH/分钟线）选择 |
| 关键后端依赖 | 新增 7 类端点：portfolio / multi-strategy / optimize / optimize-all / 任务列表 / 策略库 CRUD / （可选）服务器设置 |
| 与用户 3 点需求 | 功能对齐=补全部 P0/P1；数据源独立=新功能一律读本地 vipdoc（L1Reader），不新增网络取数；去 mock=新页面只做真实接口（当前 mock 适配器已在移除中） |

**建议排期**：P0（组合回测页、策略库页）→ P1（参数寻优页、结果对比页、单标的展示增强）→ P2（服务器设置页、周期扩展）。

## 3. 特别关注专题

### 3.1 OptimizeView（参数寻优）—— 复杂度与方案评估

**上游做法**：
- 单策略寻优 = `ParamGridOptimizer`：对勾选的 1–2 个参数的取值做**笛卡尔积**（上限 200 点），每点调一次 `BacktestEngine`，按 total_return 降序返回排名 + 最优 + （2 参数时）热力图。**网格枚举是确定性搜索，不是随机**。
- 一键寻优 = 遍历 `STRATEGY_PRESETS` 预设网格逐策略跑，`ProcessPoolExecutor` 并行（workers≥2），返回全局排名。

**Kuantix 可行性评估**：✅ 可行，无需引入新引擎。
- Kuantix 的 `BacktestBridge.run_strategy_backtest` 已封装"按策略名+参数跑一次 BacktestEngine 并返回完整结果"。`OptimizeService` 只需：网格枚举（itertools.product）→ 循环调 bridge → 汇总排名/最优/热力图。纯计算、无网络、读本地 vipdoc，符合"数据源独立"。
- **复杂度**：低–中。单策略寻优 = 循环调 bridge（与现有 BacktestService 同层）；一键寻优 = 加进程池并行（可二期，先串行）。
- **前端**：O-1 组件需策略 schema 带 `preset_grid`（上游 `StrategySchemaResponse` 已含 preset_grid 字段，Kuantix B1 `list_strategies` 目前只透传 name/label/description/params —— **需后端补透传 preset_grid**）。
- 建议：**P1 首期做单策略寻优（O-1~O-6），一键寻优（O-7）二期**；网格上限 200 沿袭上游。

### 3.2 PortfolioView（组合回测）—— 资金分仓语义

**上游语义**（PortfolioBacktestEngine）：
> "1 策略 × N 标的，**共享资金池** total_cash，按 equal 均分到各标的（每只 total_cash/N 独立跑），combined_equity = 各标的净值按日期对齐（金额）求和。"

**Kuantix 现状语义**（BacktestService._combine）：
> "逐标的独立回测（每只都拿全量 cash）→ 归一化净值（起始=1）**等权平均**。"

**结论**：两者**不等价**。Kuantix 现有组合是"归一化等权平均"，等价于上游 CompareView 的叠加图+平均；上游 PortfolioView 是"资金分仓"，组合净值代表真实资金曲线（含仓位/现金管理）。

**产品判断**：用户"选股回测"（上轮 P0）是**从选股结果池对多标的批量回测看孰优孰劣**——归一化平均正好满足"比较"；但用户诉求"与上游功能一致"，上游组合回测页是资金分仓语义。**建议两者并存**：
- 保留 /backtest = 选股回测（多标的归一化对比，现状不动）；
- 新增 /portfolio = 组合回测（资金分仓，对齐上游）；
- 后端组合分仓实现：每标的 `cash_i = total_cash/N` 独立跑 bridge，combined_equity 按日期对齐**金额求和**（需在 BacktestService 或新 service 增加分仓模式，等价上游 PortfolioBacktestEngine，或经 bridge 直调上游引擎——注意 R2 红线：引擎调用必须收敛在 bridge）。

### 3.3 CompareView（结果对比）

- 上游核心 = 任务列表 + 勾选 2–4 个 done 任务 + 归一化叠加图 + 8 项指标横表。
- Kuantix 依赖点唯一：**任务列表端点**。`JobManager/JobStore` 已有 jobs 表（module='backtest'），缺一个 `list(module, limit)` 查询 + `GET /api/v1/backtest/jobs?limit=` 端点；详情可复用 B3（jobs/{id}）+ B4（results/{id}）。
- 前端 CompareChart/CompareTable 可复用 /backtest 归一化多序列 ECharts 思路，工作量小。**建议 P1**（上游页面存在性对齐，但非回测闭环关键路径）。

### 3.4 StrategiesView（策略库）

- 上游存储 = SQLite strategies.db（单表：name/kind/strategy/strategy_label/params/context/trade_config/snapshot/tags/notes/created_at/updated_at/app_version），仅 CR（UD，无编辑）。
- Kuantix 现状：B1 策略是运行时列表（上游注册表枚举），**无用户收藏概念**。
- **建议 P0 做策略库页 + 后端 CRUD**：这是"保存策略/保存组合/载入重跑"闭环的存储底座，且 BacktestView/PortfolioView 的保存入口（B-10/P-7/S-9）都依赖它。
- 多策略组合回测（S-5）：N 策略 × 各自原标的，资金 1/N 均分，结果结构同 PortfolioResult（key=`{label}@{symbol}`）。实现可复用 3.2 的分仓引擎思路（每槽位独立跑 + 金额求和合并）。
- 注意：策略库是**用户数据**，必须落在 `~/.Kuantix/db/`（NF-15），绝不写 `~/.easy_tdx/`。

### 3.5 ServerSettingsView（服务器设置）

- 上游语义：TDX 服务器列表测速/热切换（运行中常驻连接）。
- Kuantix 语义差异：**数据已本地化**（vipdoc 数据湖），回测/因子/选股全程不连 TDX；`config.toml [tdx]` 静态配置 host，无运行中连接对象。NF-23 明确"本地工具、仅监听 127.0.0.1"。
- **建议 P2**：不做服务器切换页；如需对齐，做**只读"数据源/配置"页**（展示 [tdx] host、数据湖状态、vipdoc 路径），复用 D1 status 即可，零后端新增。

## 5. 给架构师的设计输入清单

1. **回测引擎调用红线（R2）**：所有新增回测类能力（portfolio / multi-strategy / optimize / optimize-all）必须经 `BacktestBridge` 扩展实现，不在业务层 import easy_tdx。推荐扩展方式：
   - `bridge.run_portfolio_backtest(stocks, cash, allocation='equal', ...)`（直调上游 PortfolioBacktestEngine）
   - `bridge.run_multi_strategy_backtest(slots, cash, ...)`（直调上游 MultiStrategyEngine）
   - `bridge.run_optimize(strategy, param_grid, df, ...)`（循环调 run_strategy_backtest 或直调 ParamGridOptimizer——注意确认 R2 允许桥内直调引擎）
2. **数据源独立**：portfolio/multi-strategy/optimize 的 K 线一律读本地 vipdoc（L1Reader），不新增 /bars 网络端点；数据不足 fail-loud（沿用 DataIntegrityError）。
3. **Job 模型复用**：新任务沿用 JobManager（module='backtest'，action 扩展），进度回调、取消、持久化、结果落 BacktestResultStore 全复用；JobStore 需补 list 查询（API-6）。
4. **结果结构对齐**：portfolio / multi-strategy 结果统一为 PortfolioResult 形状（total_performance / individual_results / equity_allocation / combined_equity），前端图表组件可复用。
5. **策略库存储**：新建 StrategyStore，单表 SQLite，字段对齐上游（含 kind='single'|'portfolio'|'multi'、context、snapshot、tags）；载入依赖 URL query 深链（B-11）。
6. **URL 深链约定**：回测页/组合页/寻优页统一支持 query 回填（strategy/params/symbol|stocks/startDate/endDate/category），这是"策略库载入"与"寻优查看"的联动协议，需在 router/view 层统一实现。
7. **前端组件清单**（新增，可复用 EChart 封装）：KlineChart、EquityChart、MetricTable（19 项）、TradeTable、GradeBadge、GradeDetails、ParamGridPicker、OptimizeResultTable、OptimizeHeatmap、PortfolioSummaryTable、PortfolioCompareChart、CompareChart、CompareTable、StocksPicker。
8. **评级系统**：上游 `web-ui/src/grading/` 为纯前端 TS（engine + thresholds + combinedMetrics + vetoes），建议作为参考在 Kuantix 前端实现等价模块（或确认 license 允许后移植概念，不复制代码）。
9. **去 mock**：新页面一律只接真实后端（当前 api/index.ts 已移除 mock 适配器）；新增 DTO 与端点同步进 `web/src/api/types.ts` + `client.ts`。
10. **市场规则**：代码→交易所映射一律经 MarketProfile（R6）；前端展示 `SH:/SZ:/BJ:` 前缀与 Kuantix 内部 code 的转换由前端工具函数统一（参考上游 detectMarket）。
