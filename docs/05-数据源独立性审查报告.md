# Kuantix 数据源独立性审查报告

**审查人**：software-architect（架构）
**审查日期**：2026-08-02
**审查对象**：Kuantix 全部数据获取路径 vs 上游 easy_tdx（v1.20.3，pip 依赖，位于 `.venv/lib/python3.13/site-packages/easy_tdx`）
**上游约束**：NF-1（上游只读）/ NF-20（禁止写 `~/.easy_tdx`）
**审查目标**：核实"数据源独立"——所有行情/清单数据是否**直连通达信行情服务器**获取，而非依赖上游某系统（easy_tdx web 服务 / 上游本地数据缓存 / detect_tdx_home 检测本地通达信安装 / 其它间接依赖）。

---

## 1. 结论（TL;DR）

> **需求 1 已由现有架构满足。**
>
> Kuantix **全部 8 条数据获取路径均为直连通达信行情服务器（7709/7727）或读取 Kuantix 自有数据湖（`~/.Kuantix/vipdoc`）**，**不存在**对上游 easy_tdx 任何间接数据系统的依赖：
>
> - ✅ 无任何 `easy_tdx.web`（上游 FastAPI web 服务）import；
> - ✅ 无任何 `detect_tdx_home` 调用（本地通达信安装目录检测被列入禁用清单）；
> - ✅ 无任何上游 `resolve_vipdoc` 自动路径回退（Kuantix 全部显式传文件路径，从不传 `vipdoc=None`）；
> - ✅ 无任何环境变量/配置指向 `~/.easy_tdx` 或本地通达信数据目录（`[paths]` 全部落在 `~/.Kuantix`，且 `PathsConfig.ensure()` 显式拒绝写入 `~/.easy_tdx`）；
> - ✅ 已知主机列表（known_hosts）**只读** `~/.easy_tdx/config.json`（NF-20 允许读），指纹校验证明无写入；
> - ✅ 唯一的上游"依赖"是**在进程内复用其客户端类与离线编解码函数**（`import easy_tdx.*`，NF-1 允许），这是代码复用而非数据源依赖——K 线/清单数据全部由 Kuantix 直连服务器自行拉取。

结论的完整证据见 §4 判定表（每条路径 → 直连/间接依赖 → 判定 → 文件:行号证据）。

### 3.2 `easy_tdx.web`（上游 web 服务）排查

- Kuantix 侧：`grep -rn "easy_tdx.web" Kuantix/` → **0 命中**。
- 前端侧：`web/.env.development` 的 `VITE_API_BASE=http://127.0.0.1:8899/api/v1`（Kuantix 自有后端），`web/vite.config.ts` 无任何指向上游 web 的 proxy/target。
- 上游侧：`easy_tdx/web/` 目录存在（FastAPI app + routers），但仅在上游自身 `easy-tdx serve` CLI 下运行；Kuantix 从不调用上游 CLI，也不启动该服务（§3.8 subprocess 排查）。

**结论**：✅ 无对上游 web 服务的任何依赖。Kuantix 的后端（`Kuantix serve`，端口 8899）是独立实现。

### 3.3 禁用上游工厂方法（写 `~/.easy_tdx` 的高危入口）

`adapters/tdx_client.py:70-77` 明确定义禁用清单：

```python
FORBIDDEN_UPSTREAM_FACTORIES = (
    "from_best_host", "save_best_host", "save_best_mac_host",
    "save_best_mac_ex_host", "detect_tdx_home", "get_security_list_all",
)
```

- `from_best_host` / `save_best_*`：内部会写 `~/.easy_tdx/config.json` —— 全库 **0 调用**；
- `detect_tdx_home`：检测本地通达信安装目录（`~/new_tdx` 等）—— 全库 **0 调用**，且被列入禁用清单；
- `get_security_list_all`：会把结果缓存写进 `~/.easy_tdx/cache` —— 全库 **0 调用**（`universe.py` 用 `get_security_list` 逐页手动枚举，RD-10）。

**构造防线的双重保证**：`tdx_client.py:437-477` `_construct` 显式传 `host=spec.host, port=spec.port, timeout=spec.timeout` 构造客户端，随后 `_assert_host_honoured`（`tdx_client.py:479-497`）校验 `client._host == spec.host` 且 `client._port == spec.port`，不一致立即抛 `DataIntegrityError`——即使上游内部偷偷走了自动优选也会当场暴露。

### 3.4 环境变量 / 配置指向上游数据目录

- `config.toml:25-32` `[paths]`：`root/vipdoc/factors/db/logs/reports/exports` **全部**在 `~/.Kuantix/` 下；
- `config.py:112-125` `PathsConfig.ensure()`：显式拒绝任一受管目录落在 `~/.easy_tdx` 之内（NF-1 红线），且环境变量覆盖（`Kuantix__PATHS__*`）在构造 `PathsConfig` 前合并进配置字典，同样受该检查约束；
- Kuantix **不读** `TDX_HOME`、`EASY_TDX_CONFIG_DIR`、`EASY_TDX_WEB_DIST` 等上游环境变量（全库 grep 0 命中，除 `known_hosts.py:41` 硬编码的 `~/.easy_tdx/config.json` 只读路径外）。

**结论**：✅ 无任何配置/环境变量指向上游数据目录。

### 3.5 `resolve_vipdoc` 自动路径回退的风险边界

上游 `easy_tdx/offline/paths.py:44` 的 `resolve_vipdoc(path=None)` 在**不传 path** 时会自动检测本地通达信安装目录（`TDX_HOME` 环境变量 → `~/new_tdx` 等）——这是本审查最需要确认的隐藏依赖点。

核实结果：**Kuantix 从不触发该回退**。Kuantix 调用的全部上游离线函数**签名强制要求显式文件路径**（见 3.6），且 Kuantix 侧调用点一律显式传路径：

| 上游函数 | 签名 | Kuantix 调用点 |
|---------|------|--------------|
| `read_daily_bars(filepath)` | 必填 | `factor_bridge.py:88`（`read_daily_bars(path)`）、`vipdoc_writer.py:755`（`read_daily_bars(target)`） |
| `read_ex_daily_bars(filepath)` | 必填 | `factor_bridge.py:108`、`vipdoc_writer.py:811` |
| `read_5min_bars(filepath)` | 必填 | `vipdoc_writer.py:487` |
| `get_last_bar_date(filepath)` | 必填 | `vipdoc_writer.py:367` |
| `sync_daily_bars_from_security_bars(filepath, ...)` | 必填 | `vipdoc_writer.py:331` |
| `sync_ex_daily_bars(filepath, ...)` | 必填 | `vipdoc_writer.py:420` |
| `append_5min_bars(filepath, ...)` | 必填 | `vipdoc_writer.py:481` |

上游唯一带 `vipdoc=None → 自动检测` 的函数是 `offline/finders.py` 的 `find_*_bar_file` 与 `daily_bar.py:128` 的 `read_daily_bars_by_code` —— **Kuantix 0 调用**。

**结论**：✅ 读侧/写侧所有 vipdoc 访问都基于 Kuantix 自有路径（`~/.Kuantix/vipdoc`，由 `L1Reader.root` / `VipdocWriter.root` 统一构造），不会落到 `~/.easy_tdx` 或本地通达信目录。

### 3.6 known_hosts 只读性（NF-20）

## 5. 唯一间接接触面（合法，非数据依赖）

Kuantix 对上游 easy_tdx 的依赖是**代码级复用**（pip 依赖，NF-1 允许），具体为：

1. **客户端类**：`TdxClient` / `MacClient` / `MacExClient`（负责通达信 TCP 协议编解码）——但 host/port/timeout **全部由 Kuantix 显式注入**，且禁止 `from_best_host`，构造后校验实际主机。
2. **离线编解码函数**：`read_daily_bars` / `write_daily` 等（vipdoc 二进制格式的读写）——**全部显式传 Kuantix 自有路径**。
3. **引擎类**：`BacktestEngine` / `FactorEngine` / `SignalScanner` / `ChanlunAnalyser` 等——在 Kuantix 进程内对已加载数据计算，不触网。
4. **系数表**：`easy_tdx.offline.daily_bar._SECURITY_COEFFICIENTS`（NF-25 引用非复制）。

这些属于"复用上游协议/算法实现"，与"数据源依赖"是两回事：**没有**任何一条数据是 Kuantix 从"上游系统"（web 服务、上游本地缓存、上游检测到的通达信安装目录）间接取得的。

## 6. 若需改造的场景（本报告结论下不需要，仅备案）

**结论：无需改造。** 若未来某处违反本架构引入间接依赖（例如：有人把 `scan_signals` 的 `vipdoc_path` 传 `None`、有人改用 `read_daily_bars_by_code(code)` 不带路径、有人引入 `easy_tdx.web`），最小改造方案（不违反 NF-1）为：

1. **在 `BacktestBridge`/`L1Reader` 增加路径断言**：所有上游离线函数调用点强制 `assert path.is_absolute() and "~/.Kuantix" in str(path)`（或统一经 `L1Reader.root` 构造，禁止裸路径）。
2. **扩展 R3 红线**：静态扫描禁止 `import easy_tdx.web`、禁止 `vipdoc=None` 形式的调用、禁止 `from easy_tdx.offline.paths import resolve_vipdoc, detect_tdx_home`。
3. **保持 FORBIDDEN 清单只增不减**：任何新增的上游"自动检测/自动缓存"入口一律先列入 `FORBIDDEN_UPSTREAM_FACTORIES` 再讨论是否使用。
