### 2.1 Portfolio（P0，组合回测·资金分仓）

**P1 `POST /api/v1/portfolio/run`** —— 触发组合回测，返回 Job 信封（module=`backtest`, action=`portfolio`）。

请求 `PortfolioRunRequest`（与 B2 字段集对齐，语义为"总资金分仓"）：

```jsonc
{
  "market": "CN",
  "codes": ["600519", "000001"],        // 1..20，组合标的池
  "strategy": "ma_cross",                // 单一策略（组合=1策略×N标的）
  "params": {"fast": 5, "slow": 20},
  "start": "2020-01-01",
  "end": "2025-12-31",
  "cash": 1000000,                       // 组合总资金，按 N 均分
  "commission": 0.0003, "min_commission": 5.0, "stamp_tax": 0.001,
  "slippage": 0.0, "execution": "next_open"
}
```

响应：`Job`（status 生命周期 queued→running→done；done 时 `result_summary` 含 `{strategy, codes, result_count, skipped_count, total: {total_return, annual_return, total_stocks, total_cash, combined_points}}`）。

**P2 `GET /api/v1/portfolio/jobs/{job_id}`** —— 进度轮询（返回 `Job`；不存在→404）。实现 = 转发 `container.jobs.get(job_id)`（与 B3 同逻辑）。

**P3 `GET /api/v1/portfolio/results/{job_id}`** —— 完整组合结果（不存在/未就绪→404）。响应 `PortfolioResult`：

```jsonc
{
  "total_performance": {"total_return": 0.2643, "annual_return": 0.052, "total_stocks": 2, "total_cash": 1000000},
  "individual_results": {
    "600519": { "performance": {...19项}, "equity_curve": [...], "trades": [...], "positions": [...], "config": {...} },
    "000001": { /* 同上 */ }
  },
  "equity_allocation": {"600519": 0.5, "000001": 0.5},
  "combined_equity": [ {"datetime": "2020-01-02", "total": 1000000.0, "drawdown": 0.0, "drawdown_pct": 0.0}, ... ]
}
```

> `combined_equity` 含 `drawdown_pct`——组合评级（5 维）的输入，前端可直接消费（对齐上游 combinedMetrics.ts 依赖）。

## 3. 引擎语义评估（重点）

### 3.1 PortfolioBacktestEngine 包装（D-1/D-8）

**上游能力确认**（已实测读源码 `easy_tdx/backtest/portfolio_engine.py`）：
- `PortfolioBacktestEngine(strategy, stocks: list[StockData], total_cash, allocation="equal", ...)` → `run()` 返回 `PortfolioResult`；
- 内部：`per_stock_cash = total_cash / N` → 每标的独立跑 `BacktestEngine` → `_aggregate_performance` → `_build_combined_equity`（各标的净值按日期并集 ffill 对齐后**金额求和**）→ `combined_equity` 列 = datetime/total/drawdown/drawdown_pct；
- `PortfolioResult.to_dict()` 输出 total_performance / individual_results / equity_allocation / combined_equity——**与 PM §5.4 要求的结果结构完全一致**，D-8 金额求和由上游原生满足。

**两种实现路径**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | `BacktestBridge.run_portfolio_backtest(stocks, total_cash, ...)` 桥内直调上游 `PortfolioBacktestEngine` | 语义精确对齐（含 equity_allocation/金额求和/combined_equity 原生结构）；少维护；R2 允许桥内直调引擎 | 依赖上游引擎演进（有版本校验可兜底） |
| B | 自写分仓循环：每标的 cash_i=total_cash/N 调现有 `run_strategy_backtest`，再自写"按日期对齐金额求和" | 完全复用现有桥方法 | 重复实现上游已做对的金额求和/对齐逻辑（易出 off-by-one、对齐口径漂移）；代码 +40 行 |

**推荐 A**。桥内签名（草案）：

```python
def run_portfolio_backtest(
    self, stocks: list[tuple[str, str, pd.DataFrame]],  # (code, exchange, df)
    strategy_name: str, params: dict, total_cash: float,
    *, commission=..., min_commission=..., stamp_tax=..., slippage=..., execution="next_open",
) -> dict[str, Any]:  # PortfolioResult.to_dict() 已清洗
```

实现要点：
1. 数据源：`L1Reader.read_daily_frame(exchange, code)` 读本地 vipdoc（列 datetime/open/high/low/close/vol/amount，与上游引擎输入一致），**零网络**；
2. `strategy = get_registry().get(name).build(params)` 构造实例（与 `run_strategy_backtest` 同模式）再传入引擎；
3. 结果经 `_serialize_result`/`_clean_value` 清洗 NaN/Inf → null（NF-12）；
4. 单标的读取失败：沿用 `DataIntegrityError` → 跳过并记 `skipped`（与 BacktestService 现有模式一致）；全部失败 → fail-loud 422。

### 3.2 ParamGridOptimizer 包装（D-4）

**上游能力确认**：`ParamGridOptimizer(strategy_name, param_grid, df, cash, ...)` → `run()` 返回 `OptimizeResult`（results 降序/best/heatmap/param_names）；构造时校验 `网格 ≤ MAX_GRID_POINTS(200)` 与空网格（抛 ValueError）。

**推荐**：桥内直调（与 Portfolio 同理）——

```python
def run_optimize(self, df: pd.DataFrame, strategy_name: str,
                 param_grid: dict[str, list], *, cash=..., commission=...,
                 execution="next_open", max_grid_points: int = 200) -> dict[str, Any]:
```

实现要点：
1. 单标的单 df（O1 请求即单 code）；
2. 网格大小**桥内二次校验**（≤200，>200 → `DataIntegrityError` → 400，fail-loud 不依赖前端）；
3. 结果 `OptimizeResult.to_dict()`（已含 NaN→None 清洗，见 optimizer.py 的 clean()）→ 桥内再经 `_clean_value` 兜底；
4. **不需要"多次调 B2"**——ParamGridOptimizer 本身就是"循环跑 BacktestEngine"的实现，直接包装更稳、语义一致；
5. O4 一键寻优（二期）：可 `ProcessPoolExecutor` 遍历 `STRATEGY_PRESETS`（经 bridge 只读获取），草案预留端点，不展开。

### 3.4 D-3 评级系统——**重点评估**

**结论先行：上游评级逻辑为 100% 纯前端 TypeScript，Python 包内无任何实现；Kuantix 后端无需新增评级端点，也无需 import/包装——改为前端新建 TS 评级模块（按规格重实现）。**

**证据**：
1. `grep -rln "grade|Grade|rating" easy_tdx/*.py`（Python 包全量）→ **0 命中**（实测 v1.20.3 已安装包 + easy_tdx-main 源码树）；
2. 评级实现位于 `easy_tdx-main/web-ui/src/grading/`，5 个 TS 文件：`types.ts`（Grade 档位/阈值表）、`thresholds.ts`（维度锚点）、`engine.ts`（插值/加权/否决核心）、`combinedMetrics.ts`（组合净值重算）、`index.ts`（3 场景函数：`gradePerformance` 6 维 / `gradePortfolio` 5 维 / `gradeGridPoint` 4 维 + `applyVetoes` 一票否决）；
3. **不是 `easy_tdx.web` 下的 Python 模块**——上游 web 路由只做 HTTP 转发，评级计算在浏览器端；
4. 因此：无法经 `backtest_bridge` 包装（无 Python 可包），也无法 `import easy_tdx.web.grading`（不存在）。

**评级所需输入指标，Kuantix 后端 B4 已全部具备**（实测 `easy_tdx/backtest/performance.py:214-237` `PerformanceAnalyzer.compute()` 输出）：
- 单标的 6 维：calmar ✓ max_drawdown ✓ win_rate ✓ profit_factor ✓ sharpe ✓ volatility ✓
- 组合 5 维：calmar/sharpe/sortino/volatility/max_drawdown + max_dd_duration（来自 combined_equity 净值重算，P3 已含 drawdown_pct）✓
- 寻优 4 维：sharpe/max_drawdown/win_rate/profit_factor（O3 results 已含）✓
- 一票否决输入：profit_factor ✓ total_trades ✓ max_drawdown ✓ win_rate ✓

**实现方案**（推荐）：

```
web/src/grading/
├── types.ts          # Grade 档位/GRADE_META/GRADE_THRESHOLDS（S≥88/A≥73/B≥58/C≥43/D）
├── thresholds.ts     # 维度锚点表（calmar/sharpe/sortino/max_drawdown/volatility/max_dd_duration/win_rate/profit_factor）
├── engine.ts         # interpolate（线性插值）+ scoreDimension + weightedTotal + buildResult（否决取更差档）
├── combinedMetrics.ts# 从 combined_equity 重算组合级指标（含 drawdown_pct 优先路径）
├── index.ts          # gradePerformance(6维) / gradePortfolio(5维) / gradeGridPoint(4维) + applyVetoes + downweightUnreliableDimensions
└── __tests__/        # 单测（阈值边界/否决触发/样本不足降权）
```

- **按规格重实现，不逐行复制**：阈值锚点、权重（单标的 calmar18/回撤17/胜率17/利润因子18/夏普15/波动率15；组合 25/22/22/15/16；寻优 30/28/22/20）、一票否决规则（profit_factor<1→D、回撤>60%→D、胜率<25% 且样本足→D、回撤>50%→最高B、胜率<30%→最高C、利润因子<1.2→最高B、样本<10 笔降权 win_rate/profit_factor）——这些是**规格**，从上游只读文档化后按规格实现；代码全新编写 + 单测锁定。
- **NF-25 精神说明**：NF-25 的"引用非复制"针对的是 Python 系数表（可 import 的场景）；评级在 Python 侧**无 import 对象**，属"前端规格移植"。若 license（上游为开源）允许参考，可对照锚点数值；代码结构不照搬。
- **后端零新增**（无需 `GET /backtest/grading/{code}`）：评级是 `performance` 的纯函数，前端拿到 B4 结果即可算。若未来需多端复用（如 CLI 输出评级），P1 后可选在 `Kuantix/backtest/` 增 `grading.py`（Python 重实现同规格）——**需主理人裁决是否值得双实现**（见 §6 决策 1）。
