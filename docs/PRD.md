### 0.3 关键架构发现：用上游写入器自建 vipdoc 数据湖

本机没有通达信离线数据，直觉方案是"自建 Parquet 数据湖"。但我核对源码后发现**有更优解**，请架构与研发重点关注：

1. **`resolve_vipdoc(path)` 对显式传入的路径只校验"是不是目录"**，不校验是否真实通达信安装（`paths.py:52-56`）。因此 Kuantix 可自建 `~/.Kuantix/vipdoc/` 并直接传入。
2. **上游已提供完整的 vipdoc 写入能力**：`sync_daily_bars_from_security_bars()`（A股 .day）与 `sync_ex_daily_bars()`（港美股扩展市场），后者签名只要 `filepath + bars`，**目录布局完全由 Kuantix 掌控**。
3. **增量与容错是白送的**：`get_last_bar_date()` 天然给出断点位置；`append_daily_bars()` 内部做**日期去重**、崩溃残留半条记录的 `_repair_tail()` 修复、以及 `flush + fsync` 强制落盘。

**结论**：数据湖底层应落成 **vipdoc 原生二进制格式**，而非另起炉灶。收益是——
- `SignalScanner(vipdoc_path="~/.Kuantix/vipdoc")` **无需任何改造即可全市场扫描**；
- `read_daily_bars` / `read_5min_bars` 等全部读取侧 API 立即可用；
- 增量更新、断点续传、去重、崩溃修复**全部复用上游已验证实现**，Kuantix 只写编排逻辑。

因此数据层采用**双层结构**：
- **L1 行情湖（vipdoc 二进制）** —— 原始 OHLCV，兼容上游全部读取器与扫描器；
- **L2 因子库（Parquet + SQLite）** —— L1 派生的因子值与元数据，服务分析与回测。

#### 0.3.1 ⚠️ 数据正确性红线（架构评审逐文件核实，研发必读）

"读侧零改造"成立，但**写侧有三个会导致静默数据损坏的陷阱**。这不是架构细节，而是**产品正确性红线**——一旦踩中，所有因子值、回测结论、选股清单全部错误且**表面看不出异常**。已固化为 P0 验收项与 NF-25~NF-27。

| # | 陷阱 | 后果 |
| --- | --- | --- |
| **T1** | **读写系数必须一致**。`encode_daily_bar` 用**调用方传入**的 `price_coeff/vol_coeff`；而 `read_daily_bars` 是从**文件名代码段**反推系数（`daily_bar.py:15-27` 系数表 + `:30-72` `_detect_security_type` + `:88-89` 取值）。两者不一致即解码错误。 | 写 ETF 用 A 股系数 `(0.01,0.01)`、读侧判定 `SH_FUND` 用 `(0.001,1.0)` → **价格差 10 倍、成交量差 100 倍** |
| **T2（最隐蔽，危害最大）** | **UNKNOWN 静默兜底**。`_detect_security_type` 对不认识的代码段返回 `"UNKNOWN"`，但 `:88-89` 的 `.get(sec_type, (0.01, 0.01))` **把 UNKNOWN 静默兜底成 A 股系数**——恰好抵消了该函数 docstring 声明的"避免误判"意图。<br>**范围比"个别代码段"更大**：`_detect_security_type` 以 `exchange = base[:2]` 取前缀，只有 `"sz"` / `"sh"` 两个分支。当前缀为 `"bj"`（北交所）时**两个分支全部落空**，直接掉到函数末尾 `return "UNKNOWN"` → **整个北交所市场都走静默兜底路径**，而非仅某些代码段。`_market_to_exchange` 同样只映射 SZ/SH。 | 非常规代码段与**整个北交所****不报错、不告警**，直接按 A 股系数解码出错误价格 |
| **T3** | **fsync 与崩溃修复只有 A 股日线有**。实测：`write_daily.py` 含 `fsync`×2、`_repair_tail`×4；`write_ex_daily.py` 与 `write_min_bar.py` **均为 0**，且 ex/min 读侧无 `_repair_tail` 对应修复。 | 港美股与分钟线写入中途崩溃 → 残留半条记录且**无自动修复**，后续读取错位 |

**产品层要求**（写入 P0 验收）：
1. **系数感知写入**：DataLake 写入器必须与 `_SECURITY_COEFFICIENTS` **共用同一张系数表**（从上游读取，禁止在 Kuantix 侧硬编码复制），按目标文件名反推应用系数——即"**用读侧的判定逻辑决定写侧的系数**"。
2. **UNKNOWN 显式拒绝**：写入前若证券类型判定为 `UNKNOWN`，**必须显式报错并跳过该标的、记入异常日志与隔离区**，严禁沿用兜底系数静默写入。P0 股票池明确**不含北交所**（如需支持列为 P1 并单独验证）。
3. **写后回读校验**：ex/分钟线写入后自行补 `fsync`；每个标的写入完成后**回读末尾 N 条与源数据比对**（价格容差 <0.001），不一致即标记该标的数据污染、**进入隔离区清单**并告警。

> 这三条的共同特征是：**失败时不会抛异常，只会让所有下游结论悄悄变错**。因此校验必须前置到写入环节，而不是等用户发现回测结果离谱。
>
> **这类缺陷的本质**：作者在 `_detect_security_type` 的 docstring 里明确表达了"不要误判"的防御意图，却被调用点一个 `.get(..., (0.01, 0.01))` 原样抵消——**防御意图在调用点失效**。在量化系统里，"错得很自信"比崩溃严重得多：崩溃至少你知道出事了，错价会一路流进因子、回测、选股，最终等价于**资金损失**。这正是 NF-26 被提升为全项目通用原则的原因（见 5.0）。

> **技术约束提示（重要）**：通达信协议为**请求-响应式，无服务端推送**。所谓"实时行情订阅"只能以**定时轮询 `get_stock_quotes_list` 批量拉取**实现（该接口支持批量传入代码列表）。这决定了监控模块的最小时间粒度为秒级（建议 3–5 秒），**无法做到 tick 级逐笔推送**，PRD 全篇按此前提设计。

## 1. 产品目标

> **一句话定位**：Kuantix 是构建在 easy-tdx 之上的**本地化个人量化工作台**，把"因子研究 → 策略选股 → 实盘盯盘"三段割裂的流程，收敛成一条**可持久化、可调度、全程 JSON 可编程**的闭环。

**三条核心价值：**

1. **让因子研究可沉淀** —— 上游因子每次都是"算完即弃"，且本机无离线数据。Kuantix 自建本地行情湖与因子持久化，使 IC/IR、分层收益、衰减曲线可跨时间对比复算，研究成果从"一次性脚本"变成"可积累资产"。
2. **让研究成果直达实盘** —— 打通"因子模型 → 选股清单 → 监控预警 → 可下单清单"链路，研究出的因子权重能一键落到当日选股结果、自动进入盯盘队列，并导出为券商可导入的 CSV，消除全流程人工搬运。
3. **让一切能被 AI Agent 调用** —— 所有能力同时提供 CLI、REST 与**结构化 JSON 输出**，任何结果都能被 AI Agent 直接消费与二次编排，人机双入口对等。

**明确的范围边界（不做什么）：**

- ❌ **不对接券商交易 API、不做真实下单**。无订单状态机、无资金账户校验、不触碰任何委托接口。
- ✅ 替代方案：导出**券商通用可导入 CSV 清单**，由用户人工确认后自行导入交易软件执行。
- ❌ 不做机构级分布式、不做多用户权限、不引入外部中间件。

## 2. 目标用户与使用场景

### 用户 A：个人量化研究者（主要用户）

- **画像**：有 Python 基础、自建策略、**macOS 环境且未安装通达信客户端**（依赖在线协议取数）；单机运行，无运维团队；资金规模个人级；关注 A 股为主，兼顾港股美股。
- **痛点**：本地无历史数据、每次分析都要联网重拉；因子回测脚本散落各处、结果无法对比；盘中要手动盯十几只票的买卖点；选股结果靠 Excel 手工整理再手敲进交易软件。
- **典型场景**：
  - *首次使用*：一键全量拉取行情建本地数据湖，之后每日自动增量更新。
  - *周末研究*：批量算 30 个因子近 3 年值 → 落盘 → 看 IC/IR 排名 → 挑 5 个合成新模型 → 回测出报告。
  - *盘前 9:15*：定时任务自动跑选股，输出当日 Top 20 候选清单并推送到手机。
  - *盘中 10:30*：持仓股触发缠论一卖 + 跌破止损线，收到告警。
  - *调仓时*：选股结果 → 组合权重建议 → 导出 CSV → 导入券商软件执行。
  - *盘后 15:30*：自动复盘日报，看模型今日选股的实际表现与因子衰减情况。

### 用户 B：AI Agent 调用方（对等一等公民）

- **画像**：Claude / GPT 等 Agent，通过 CLI 或 REST 调用 Kuantix，消费 JSON 做推理与决策。
- **痛点**：多数量化工具只有人类 UI，输出是图表/HTML，Agent 无法解析。
- **典型场景**：
  - 用户问"最近哪个因子失效了？"→ Agent 调 `GET /api/factors/decay` → 拿 JSON → 自然语言回答。
  - 用户说"帮我选出低估值且缠论二买的票"→ Agent 组装选股条件 JSON → 调选股接口 → 返回排序清单。
  - Agent 定期拉取告警 JSON 与实盘偏离度 JSON，主动汇报持仓风险与策略健康度。

## 4. 需求池

> **P0 定义**：能跑通"建数据湖 → 注册因子 → 算并落盘 → 看 IC/IR → 合成模型 → 回测出报告 → 选股出清单 → 加入监控 → 触发告警"这条**最小闭环**的必需项。P0 刻意克制：凡上游已有算法一律复用不重写；多市场只做**接口预留**，实现只跑 A 股。

## 5. 非功能需求

### 5.0 总则：不确定即拒绝（全项目最高原则）

> **NF-26 是全项目通用原则，不限于 DataLake，优先级高于本章其余所有条目。** 任何与之冲突的设计一律以本条为准。

- **NF-26 不确定即拒绝（fail-loud）**：一切**无法确定正确性**的情形——证券类型判定为 `UNKNOWN`、市场未实现、系数缺失、因子依赖列缺失、插件加载失败、配置项缺省、数据源返回异常——**一律显式报错 + 跳过 + 记录异常日志与隔离区**，**严禁静默兜底、静默降级、静默使用默认值**。
  - **落地要求**：`core` 层必须提供统一的 fail-loud 工具（如 `require_known(value, context)` / `reject_unknown(...)`），**所有模块强制使用**，禁止各模块自行 `try/except: pass` 或 `dict.get(key, 默认值)` 兜底。
  - **代码审查红线**：对可能取不到值的查表操作，**禁止提供"看起来合理"的兜底默认值**（这正是上游 T2 陷阱的成因）。
  - **原则**：宁可少一只标的、少一个功能，不可多一条错数据。
  - **理由**：在量化系统里，"错得很自信"的缺陷等价于**资金损失**，比崩溃严重得多——**崩溃至少你知道出事了**。用户会基于错误信号真金白银下单，且界面上一切正常，往往在亏损后才发现。

### 5.1 解耦与可插拔

- **NF-1 上游只读**：Kuantix **禁止**修改、复制、vendor 上游任何源码文件；仅通过 `pip install easy-tdx==1.20.3` 依赖后 `import` 使用。所有上游调用需**收敛到 `Kuantix/adapters/` 单一适配层**，上游升级时只改这一层。
- **NF-2 插件式注册**：因子、预警判据、**推送通道**、选股过滤器、**券商 CSV 模板**、**市场档案**六类扩展点均采用**装饰器注册 + 目录自动发现**模式（与上游 `register_factor` 风格一致），新增扩展**零改框架代码**。
- **NF-3 模块边界**：`data` / `factor` / `monitor` / `screen` 四大模块**不得互相直接 import**，跨模块交互一律通过 `Kuantix/core/` 的数据契约与事件总线。
- **NF-4 分层**：`adapters`（上游封装）→ `core`（领域模型与契约）→ `services`（业务编排）→ `api`（FastAPI/CLI）四层单向依赖，下层不感知上层。

### 5.2 多市场隔离（新增）

- **NF-5 市场规则外置**：交易日历、交易时段（含午休）、涨跌幅限制、最小变动价位、每手股数、货币单位、时区、复权口径、代码格式**一律由 `MarketProfile` 提供**，业务代码**严禁硬编码** A 股假设（如 ±10%、100 股一手、252 交易日、CNY、UTC+8）。
- **NF-6 市场标识贯穿全链路**：数据湖分区、因子值、选股结果、监控标的、告警、导出清单**均携带 market 字段**；跨市场数据**不得混算**（如不同货币的持仓市值需分别汇总后再按汇率折算，汇率缺失时明确标注而非静默相加）。
- **NF-7 接口先行、实现分期**：P0 阶段三市场接口全部定义到位并有 A 股完整实现，港美股以"未实现"显式抛错（而非静默降级为 A 股规则）；P1 补齐实现时**不得改动接口签名**。
- **NF-8 时区安全**：所有时间戳内部统一以带时区的 UTC 存储，仅在展示层按 MarketProfile 时区渲染；跨市场调度按各自本地时间触发。

### 5.3 JSON 输出契约（AI Agent 适配）

- **NF-9 统一信封**：所有 JSON 响应结构一致：
  ```
  { "code": 0, "message": "ok",
    "data": { ... },
    "meta": { "generated_at": "...", "data_date": "...", "market": "CN",
              "elapsed_ms": 123, "version": "..." } }
  ```
- **NF-10 双入口对等**：任何能力必须同时可通过 **CLI（`--json`）** 与 **REST** 获取，且两者返回**同一份 schema**，不得出现"只有 Web 有"的功能。
- **NF-11 Schema 可发现**：Pydantic v2 定义全部模型，导出 JSON Schema 与 OpenAPI，供 Agent 自省。
- **NF-12 数值安全**：JSON 中禁止出现 `NaN`/`Infinity`（非法 JSON），统一序列化为 `null`；浮点保留 6 位小数。
- **NF-13 自解释**：关键指标字段附带中文名与单位（通过 schema description），Agent 无需外部文档即可解释结果。

### 5.4 性能预期（单机个人场景，非机构级）

### 5.5 部署形态

- **NF-14 单机单进程优先**：一条命令 `Kuantix serve` 同时起 REST + 监控循环 + 调度器；不引入 Redis / Kafka / Celery 等外部中间件。
- **NF-15 零外部数据库**：存储仅用 **SQLite**（元数据、持仓、规则、告警、选股结果）+ **Parquet**（因子值）+ **vipdoc 二进制**（原始行情）；开箱即用免安装。
- **NF-16 配置文件驱动**：单个 `config.toml` 管理端口、轮询间隔、推送通道、数据路径、市场开关；敏感信息（Webhook token、SMTP 密码、Bark key）支持环境变量覆盖，**不入版本库**。
- **NF-17 端口隔离**：Kuantix 默认端口独立于上游 `easy-tdx serve`，两者可同时运行互不干扰。
- **NF-18 数据目录**：默认 `~/.Kuantix/`（可配置），含 `vipdoc/`（L1 行情湖）、`factors/`（L2 因子库）、`db/`、`logs/`、`reports/`、`exports/`（下单清单）。**与上游 `~/.easy_tdx/` 完全隔离，不写入上游目录。**
- **NF-19 平台**：支持 macOS / Windows / Linux；Python ≥ 3.10（与上游一致）。首要验证平台为 **macOS**（用户当前环境）。
- **NF-20 复用上游连接配置**：可选读取 `~/.easy_tdx/config.json` 中已测速的最优节点作为默认连接（**只读不写**），免去用户重复测速。

### 5.6 安全与边界

- **NF-21 严禁下单**：代码库中**不得包含**任何券商交易接口、委托下单、资金划转相关实现或依赖。导出清单为纯文本文件产物。
- **NF-22 导出物免责标注**：所有下单清单文件头部与 Web 导出确认弹窗均需标注"仅供人工核对参考，非自动交易指令"。
- **NF-23 本地监听**：默认仅监听 `127.0.0.1`，不做鉴权；如需远程访问由用户自行加反向代理并自担风险。
- **NF-24 限速与礼貌抓取**：数据湖拉取需内置请求限速与退避重试，避免因高频请求被行情服务器断连或封禁。
- **NF-28 监控链路与回补链路资源隔离（P0 硬性，非优化项）**：实盘监控轮询与数据回补**必须使用独立的连接/进程，并支持错峰调度**（默认：交易时段禁止后台全量回补，仅允许盘后与非交易日执行；用户强制启动时需二次确认并显式告警）。
  - **理由**：二者共用连接会互相限速，导致**盘中告警延迟**。这不是性能问题而是**资金风险**——告警晚 30 秒可能就是一个跌停板。因此列为 P0 硬性约束而非优化项。
  - 验收：交易时段启动全量回补时，监控轮询的实际间隔与告警延迟**不得超过配置值的 1.5 倍**。

### 5.7 数据正确性（新增，最高优先级）

> 依据 0.3.1 的三个静默损坏陷阱。这类缺陷**不会抛异常**，只会让所有因子值、回测结论、选股清单悄悄变错，用户往往在真金白银亏损后才发现。因此正确性保障必须**前置到写入环节**。

- **NF-25 编解码对称性（硬性，不可协商）**：任何写入 L1 的路径，其使用的价格/量系数**必须与上游读侧 `_SECURITY_COEFFICIENTS` 的判定结果一致**。系数表**必须从上游 `import` 引用，严禁在 Kuantix 侧复制、粘贴或硬编码任何副本**。
  - **理由（这条必须写死）**：一旦复制一份，上游哪天更新代码段划分（例如补上北交所、新增 ETF 代码段），我们这份副本就变成**错的，而且照样不报错**——退化成 T1/T2 同类的静默损坏。引用则自动跟随上游演进。
  - CI 需有单元测试覆盖"写入→回读→数值一致"，覆盖 A股/ETF/指数/债券**至少四类**证券；并有静态检查确保代码库中不存在系数表副本。
- **NF-26 不确定即拒绝** → **已升级为全项目通用原则，见 5.0 总则**。本节场景为其在数据层的具体应用：证券类型 `UNKNOWN`、市场未实现、系数缺失一律显式报错跳过并入隔离区。
- **NF-27 写后校验与隔离区**：每标的写入完成后回读末尾 N 条与源数据比对；不一致则在元数据库中标记为"数据污染"。
  - **不能只是静默跳过**——必须落地为**持久化的「隔离区清单」**，记录：标的代码、隔离原因（UNKNOWN 类型／回读不一致／拉取失败）、发生时间、最后一次尝试时间。
  - 后续因子计算与选股**自动排除**隔离区标的，**并在 Web 页面与 JSON `meta` 中显式提示"本次结果已排除 N 只标的"**，可下钻查看清单与原因。
  - **理由**：用户必须知道哪些票没有数据、为什么没有。否则会以为选股结果覆盖了全市场，实际上悄悄漏了一批——这本身又是一种"错得很自信"。
  - `Kuantix data verify` 与 REST 接口需能列出完整隔离区清单；重新同步成功后自动移出。

## 附录：P0 交付验收标准（闭环冒烟测试）

一次性跑通以下 10 步即视为 P0 达成：

1. `Kuantix data sync --market CN --years 10` → 在线拉取全 A 日线落盘至 `~/.Kuantix/vipdoc/`，有**进度可视化**、可**后台运行**；**中途 Ctrl+C 后重跑能断点续传**；
2. `Kuantix data verify --json` → 输出各标的数据起止日期、缺失交易日、异常记录数、**污染标的列表**的合法 JSON；
2b. **【正确性红线，见 0.3.1】** 取一只 A 股（如 sz000001）+ 一只 ETF（如 sh510300）+ 一只指数（如 sh000001），分别 `data sync` 后回读，**价格与在线源比对误差 <0.001**（验证 T1 系数对称）；构造一个代码段不在系数表内的标的（如北交所 bj430047），**必须显式报错跳过并记入异常日志，而非静默写入**（验证 T2 兜底陷阱）；
3. 在 `Kuantix/factors/` 放一个自定义因子文件 → `Kuantix factor list` 能看到它与上游内置因子；
4. `Kuantix factor compute --factors momentum_20d,pe_inv --start 2021-01-01 --end 2025-12-31` → **全程读本地数据湖不走网络**，因子值落盘为 Parquet；
5. `Kuantix factor report --factor momentum_20d --json` → 输出含 IC/IR/分层收益/换手率的合法 JSON；
6. `Kuantix factor combine --factors momentum_20d,pe_inv --method ir --save-model m1` → 模型保存成功；
7. `Kuantix factor backtest --model m1 --json` → 输出含年化/回撤/夏普/胜率/盈亏比的报告 JSON + Markdown；
8. `Kuantix screen run --model m1 --filter "chanlun:mmd_buy2" --top 20 --json` → 输出排序后的候选清单 JSON；
9. `Kuantix monitor add --from-screen latest` + 配置一条价格规则 → 启动监控 → 人为构造触发 → **收到桌面通知 + Webhook 回调** + 告警落库；
10. `Kuantix serve` → 浏览器打开三个页面，均能看到上述数据，顶栏市场切换器显示 A 股可用/港美股置灰，各页 `[导出JSON]` 可用。

**附加校验（架构约束）：**
